1. Setting Up Your Gutenberg Development Environment

When Gutenberg was first introduced, building a block required complex Webpack configurations, Babel setups, and manual dependency management. Thankfully, the core WordPress team created the official @wordpress/create-block tool, which sets up a scaffolding environment in seconds.

Before starting, make sure you have Node.js and npm installed on your local development server (such as Local, Laragon, or Docker). Open your terminal, navigate to your local site's wp-content/plugins folder, and run the following command:

npx @wordpress/create-block custom-callout-block
cd custom-callout-block
npm start

This script auto-configures a plugin with all modern build tools, hot reloading, script optimization, and code linting right out of the box.

2. Understanding Block Anatomy: The block.json File

The core metadata of any modern WordPress block lives inside the block.json file. Standardizing block attributes in this file allows WordPress to parse metadata efficiently without loading heavy JavaScript on every page render.

Here is an example structure for a custom callout block we will build:

{
  "$schema": "https://schemas.wp.org/trunk/block.json",
  "apiVersion": 3,
  "name": "shiv/callout-box",
  "version": "1.0.0",
  "title": "Custom Callout Box",
  "category": "design",
  "icon": "megaphone",
  "description": "A stylish callout box block for important notices.",
  "supports": {
    "html": false,
    "color": {
      "background": true,
      "text": true
    },
    "spacing": {
      "margin": true,
      "padding": true
    }
  },
  "attributes": {
    "content": {
      "type": "string",
      "source": "html",
      "selector": ".callout-content"
    },
    "boxType": {
      "type": "string",
      "default": "info"
    }
  },
  "textdomain": "custom-callout-block",
  "editorScript": "file:./build/index.js",
  "editorStyle": "file:./build/index.css",
  "style": "file:./build/style-index.css"
}

3. Building the Block Interface: edit.js and save.js

A native custom block relies on two primary JavaScript entry points: the editor view (edit.js) and the front-end rendering view (save.js).

The Editor Component (edit.js)

The edit.js component manages how the block behaves inside the Gutenberg admin page. Here, we use React components provided by @wordpress/block-editor and @wordpress/components to create editable content areas and sidebar controls.

import { __ } from '@wordpress/i18n';
import { useBlockProps, RichText, InspectorControls } from '@wordpress/block-editor';
import { PanelBody, SelectControl } from '@wordpress/components';
import './editor.scss';

export default function Edit({ attributes, setAttributes }) {
    const { content, boxType } = attributes;
    const blockProps = useBlockProps({
        className: `callout-box callout-${boxType}`
    });

    return (
        <>
            <InspectorControls>
                <PanelBody title={__('Callout Settings', 'custom-callout-block')}>
                    <SelectControl
                        label={__('Box Type', 'custom-callout-block')}
                        value={boxType}
                        options={[
                            { label: 'Info', value: 'info' },
                            { label: 'Warning', value: 'warning' },
                            { label: 'Success', value: 'success' }
                        ]}
                        onChange={(value) => setAttributes({ boxType: value })}
                    />
                </PanelBody>
            </InspectorControls>

            <div {...blockProps}>
                <RichText
                    tagName="p"
                    className="callout-content"
                    value={content}
                    onChange={(newContent) => setAttributes({ content: newContent })}
                    placeholder={__('Enter your notice or warning text...', 'custom-callout-block')}
                    allowedFormats={['core/bold', 'core/italic', 'core/link']}
                />
            </div>
        </>
    );
}

The Save Component (save.js)

The save.js function defines how the static HTML markup should be stored inside the database content body (wp_posts table).

import { useBlockProps, RichText } from '@wordpress/block-editor';

export default function save({ attributes }) {
    const { content, boxType } = attributes;
    const blockProps = useBlockProps.save({
        className: `callout-box callout-${boxType}`
    });

    return (
        <div {...blockProps}>
            <RichText.Content
                tagName="p"
                className="callout-content"
                value={content}
            />
        </div>
    );
}

4. Adding Front-End & Admin Styling

To style the block seamlessly across both the front-end website and the backend block editor, we write CSS within style.scss. Because WordPress automatically compiles SCSS via wp-scripts, we can write clean code:

    padding: 18px 24px;
    border-radius: 8px;
    margin-bottom: 1.5rem;

5. Registering the Block via PHP

With your compiled JS files produced in the /build folder, you simply need to register the block type in your main PHP plugin file using the init action hook:

<?php
/**
 * Plugin Name: Shiv's Custom Callout Block
 * Description: A custom Gutenberg block for callouts.
 * Version: 1.0.0
 * Author: Shiv Parmar
 * Text Domain: custom-callout-block
 */

if (!defined('ABSPATH')) {
    exit; // Exit if accessed directly.
}

function shiv_register_custom_callout_block() {
    register_block_type(__DIR__ . '/build');
}
add_action('init', 'shiv_register_custom_callout_block');

6. Practical Advice for Production Gutenberg Development

During my web development projects in Rajkot and remote client integrations across the globe, I have compiled a set of best practices for block creation:

  • Prefer Block.json over PHP registration: Always define your styles, scripts, and attributes in block.json. It improves asset loading performance because assets are conditionally loaded on pages where the block actually exists.
  • Use Dynamic Blocks for Query-Based Content: If your block fetches latest blog posts, API endpoints, or user profile data, skip save.js (return null) and utilize server-side rendering via PHP with the render_callback parameter.
  • Plan for Block Deprecations Early: When you change HTML structures in save.js, older posts will throw validation errors. Always use the block deprecation API to safely handle older markup versions gracefully.
  • Leverage Core Design Tools: Avoid hardcoding typography, margin, and color options in custom controls. Enable theme support supports in block.json so users can use native WordPress controls.

Transitioning to block development might feel intimidating if you are transitioning from traditional PHP theme building. However, once you become familiar with React components, custom hook usage, and the @wordpress/scripts package, building blocks becomes fast, predictable, and highly enjoyable.
