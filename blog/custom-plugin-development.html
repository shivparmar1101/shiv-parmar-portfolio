Building Custom WordPress Plugins from Scratch

Off-the-shelf plugins work until they don't. Once a client needs custom data structures, third-party API integrations, or behavior that no existing plugin supports, a custom plugin becomes the only viable path. Here's my approach to building production-ready WordPress plugins from scratch.

1. Plugin Architecture — Start with Structure

A well-organized plugin is maintainable and debuggable. I use a modular folder structure that separates concerns cleanly. The main plugin file acts as a bootstrap loader — it doesn't contain business logic, just autoloading and initialization:

The main plugin file registers everything through a single entry point:

<?php
/**
 * Plugin Name: My Custom Plugin
 * Version: 1.0.0
 */

defined('ABSPATH') || exit;

define('MY_PLUGIN_VERSION', '1.0.0');
define('MY_PLUGIN_PATH', plugin_dir_path(__FILE__));

require_once MY_PLUGIN_PATH . 'includes/class-plugin-core.php';

// Initialize on plugins loaded
add_action('plugins_loaded', function() {
    My_Plugin_Core::instance();
});

2. ACF-Driven Data Structures

Advanced Custom Fields gives clients a visual way to manage content without touching code. I register field groups programmatically so they ship with the plugin — not exported JSON files that can drift out of sync:

// includes/class-post-types.php
class My_Plugin_Post_Types {
    
    public function register() {
        add_action('init', [$this, 'register_post_type']);
        add_action('acf/init', [$this, 'register_field_groups']);
    }
    
    public function register_post_type() {
        register_post_type('project', [
            'labels' => [
                'name' => 'Projects',
                'singular_name' => 'Project',
            ],
            'public' => true,
            'has_archive' => true,
            'show_in_rest' => true, // Enable Gutenberg
            'supports' => ['title', 'editor', 'thumbnail'],
            'menu_icon' => 'dashicons-portfolio',
        ]);
    }
    
    public function register_field_groups() {
        if (!function_exists('acf_add_local_field_group')) {
            return;
        }
        
        acf_add_local_field_group([
            'key' => 'group_project_details',
            'title' => 'Project Details',
            'fields' => [
                [
                    'key' => 'field_project_url',
                    'label' => 'Live URL',
                    'name' => 'project_url',
                    'type' => 'url',
                    'required' => 1,
                ],
                [
                    'key' => 'field_project_tech',
                    'label' => 'Technologies Used',
                    'name' => 'project_tech',
                    'type' => 'taxonomy',
                    'taxonomy' => 'tech_stack',
                    'field_type' => 'multi_select',
                    'return_format' => 'id',
                ],
                [
                    'key' => 'field_project_gallery',
                    'label' => 'Screenshots',
                    'name' => 'project_gallery',
                    'type' => 'gallery',
                    'return_format' => 'array',
                    'min' => 3,
                    'max' => 10,
                ],
            ],
            'location' => [
                [['param' => 'post_type', 'operator' => '==', 'value' => 'project']],
            ],
        ]);
    }
}

3. REST API Integration Layer

Custom REST endpoints let you build headless frontends, mobile apps, or connect to external services without exposing WordPress internals. I always namespace my endpoints and include proper permission callbacks:

// includes/class-rest-api.php
class My_Plugin_REST_API {
    
    private $namespace = 'my-plugin/v1';
    
    public function register() {
        add_action('rest_api_init', [$this, 'register_routes']);
    }
    
    public function register_routes() {
        register_rest_route($this->namespace, '/projects', [
            'methods' => 'GET',
            'callback' => [$this, 'get_projects'],
            'permission_callback' => '__return_true',
            'args' => [
                'per_page' => [
                    'default' => 12,
                    'sanitize_callback' => 'absint',
                ],
                'category' => [
                    'default' => '',
                    'sanitize_callback' => 'sanitize_text_field',
                ],
            ],
        ]);
        
        // Authenticated endpoint for admin actions
        register_rest_route($this->namespace, '/projects/(?P<id>\d+)/sync', [
            'methods' => 'POST',
            'callback' => [$this, 'sync_project_to_external'],
            'permission_callback' => function() {
                return current_user_can('edit_posts');
            },
        ]);
    }
    
    public function get_projects($request) {
        $args = [
            'post_type' => 'project',
            'posts_per_page' => $request->get_param('per_page'),
            'post_status' => 'publish',
        ];
        
        $category = $request->get_param('category');
        if ($category) {
            $args['tax_query'] = [[
                'taxonomy' => 'project_category',
                'field' => 'slug',
                'terms' => $category,
            ]];
        }
        
        $query = new WP_Query($args);
        $projects = array_map(function($post) {
            return [
                'id' => $post->ID,
                'title' => $post->post_title,
                'url' => get_field('project_url', $post->ID),
                'thumbnail' => get_the_post_thumbnail_url($post->ID, 'large'),
                'excerpt' => wp_trim_words($post->post_content, 30),
            ];
        }, $query->posts);
        
        return rest_ensure_response([
            'projects' => $projects,
            'total' => $query->found_posts,
        ]);
    }
}

4. Hooks and Filters — The Right Way

Hooks are how your plugin communicates with the rest of WordPress. Always document which hooks you provide and accept, and use do_action / apply_filters with descriptive names that include your plugin prefix:

// After saving a project, allow other code to react
do_action('my_plugin_project_saved', $project_id, $post_data);

// Let other developers modify the output
$display_data = apply_filters('my_plugin_project_display', $data, $post_id);

// Example usage in a theme or another plugin:
add_action('my_plugin_project_saved', function($project_id) {
    // Sync to external CRM
    send_to_crm($project_id);
});

5. Client-Friendly Settings Pages

Clients don't want to edit code. I build settings pages using the WordPress Settings API that feel native and intuitive. Group related fields, add help text, and validate inputs server-side:

// includes/class-settings-page.php
class My_Plugin_Settings {
    
    public function register() {
        add_action('admin_menu', [$this, 'add_menu_page']);
        add_action('admin_init', [$this, 'register_settings']);
    }
    
    public function add_menu_page() {
        add_menu_page(
            'My Plugin Settings',
            'My Plugin',
            'manage_options',
            'my-plugin-settings',
            [$this, 'render_page'],
            'dashicons-admin-generic',
            80
        );
    }
    
    public function register_settings() {
        register_setting('my_plugin_options', 'my_plugin_settings', [
            'sanitize_callback' => [$this, 'sanitize_settings'],
        ]);
        
        add_settings_section(
            'api_section',
            'API Configuration',
            null,
            'my-plugin-settings'
        );
        
        add_settings_field(
            'api_key',
            'API Key',
            [$this, 'render_text_field'],
            'my-plugin-settings',
            'api_section',
            ['id' => 'api_key', 'description' => 'Found in your external service dashboard']
        );
        
        add_settings_field(
            'webhook_url',
            'Webhook URL',
            [$this, 'render_text_field'],
            'my-plugin-settings',
            'api_section',
            ['id' => 'webhook_url', 'description' => 'POST requests will be sent here']
        );
    }
    
    public function sanitize_settings($input) {
        $clean = [];
        $clean['api_key'] = sanitize_text_field($input['api_key'] ?? '');
        $clean['webhook_url'] = esc_url_raw($input['webhook_url'] ?? '');
        return $clean;
    }
    
    public function render_text_field($args) {
        $settings = get_option('my_plugin_options', []);
        $value = $settings[$args['id']] ?? '';
        echo '<input type="text" name="my_plugin_settings[' . esc_attr($args['id']) . '"] '
           . 'value="' . esc_attr($value) . '" class="regular-text">';
        if (!empty($args['description'])) {
            echo '<p class="description">' . esc_html($args['description']) . '</p>';
        }
    }
}

6. Making Plugins Client-Friendly

The technical implementation is only half the job. A plugin is only successful when clients can actually use it. Here are my non-negotiable practices:

  • Admin notices — Show clear status messages after actions, not cryptic errors
  • Help text — Every field should explain what it does in plain language
  • Validation feedback — Validate inline, not on page reload
  • Export/import — Let clients back up and migrate settings between environments
  • Minimal dependencies — Only require ACF Pro or other essentials; no unnecessary bloat

I also include a readme.txt following WordPress plugin standards, a changelog, and a support email. This makes future handoffs to other developers seamless.

Good plugins solve a specific problem well. Great plugins solve that problem while being maintainable, extensible, and friendly to both developers and the people who actually use WordPress every day.
