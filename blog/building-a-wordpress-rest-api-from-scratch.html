Understanding the Basics of Custom Endpoints

Before jumping into code, let us break down what happens when you create a custom endpoint. When you send an HTTP request (such as a GET or POST request) to a specific URL pattern on your WordPress site, WordPress matches that route, executes a callback function, and returns a structured JSON response.

To register a custom route safely, WordPress provides a hook called rest_api_init along with the core function register_rest_route(). Using these built-in tools ensures your custom endpoints adhere to WordPress standards and stay clean, maintainable, and fast.

Step 1: Registering a Custom REST API Route in PHP

Let us create a scenario: imagine we are building a custom endpoint to fetch a list of featured portfolio projects for a client’s mobile app. We want this endpoint to accept custom parameters, filter data securely, and output standard JSON.

You can add the following code to your custom plugin file or your theme's functions.php file:

<?php
/**
 * Register custom REST API route for Portfolio items.
 * Author: Shiv Parmar
 */

add_action('rest_api_init', 'sp_register_portfolio_routes');

function sp_register_portfolio_routes() {
    // Register route: /wp-json/sp-portfolio/v1/projects
    register_rest_route('sp-portfolio/v1', '/projects', array(
        'methods'  => 'GET',
        'callback' => 'sp_get_featured_projects',
        'permission_callback' => 'sp_get_projects_permissions_check',
        'args'     => array(
            'limit' => array(
                'default'           => 5,
                'sanitize_callback' => 'absint',
            ),
        ),
    ));
}

Let us dissect what is happening in the snippet above:

  • Namespace (sp-portfolio/v1): Prevents naming collisions between plugins and themes. Always prefix namespaces with a unique vendor string.
  • Route (/projects): The specific URL path appended to the namespace.
  • Methods: Defines the allowed HTTP method (e.g., GET, POST, PUT, or DELETE). You can also use constants like WP_REST_Server::READABLE.
  • Callback: The function that executes to handle the business logic and return data.
  • Permission Callback: Checks if the request sender has appropriate credentials or permission to access the data.
  • Args: Sanitizes and validates incoming URL parameters.

Step 2: Handling the Callback Logic and Returning Data

Now that the route is registered, we need to create the callback function sp_get_featured_projects that retrieves our custom post type data and returns a structured WP_REST_Response object.

<?php
/**
 * Get featured projects callback.
 * 
 * @param WP_REST_Request $request
 * @return WP_REST_Response
 */
function sp_get_featured_projects($request) {
    // Retrieve sanitized parameter
    $limit = $request->get_param('limit');

    $args = array(
        'post_type'      => 'portfolio',
        'posts_per_page' => $limit,
        'post_status'    => 'publish',
    );

    $query = new WP_Query($args);
    $projects = array();

    if ($query->have_posts()) {
        while ($query->have_posts()) {
            $query->the_post();
            $projects[] = array(
                'id'        => get_the_ID(),
                'title'     => get_the_title(),
                'excerpt'   => get_the_excerpt(),
                'permalink' => get_permalink(),
                'thumbnail' => get_the_post_thumbnail_url(get_the_ID(), 'medium'),
            );
        }
        wp_reset_postdata();
    }

    if (empty($projects)) {
        return new WP_REST_Response(array('message' => 'No projects found.'), 404);
    }

    return new WP_REST_Response($projects, 200);
}

Step 3: Implementing Security and Permission Checks

Security is non-negotiable when dealing with custom REST endpoints. Many developers bypass security by passing __return_true into the permission callback during development, but forgetting to secure public or sensitive routes later can open security vulnerabilities.

"Never leave custom REST API permission callbacks set to '__return_true' without verifying whether data exposure or user actions require authentication. Always validate input parameters and check capability scope using current_user_can() for sensitive data."

Here is how we can write our permissions callback function:

<?php
/**
 * Permission check for portfolio projects route.
 * 
 * @param WP_REST_Request $request
 * @return bool|WP_Error
 */
function sp_get_projects_permissions_check($request) {
    // For public GET endpoints, simple access might be allowed

    return true; // Publicly readable featured items

Step 4: Consuming the Endpoint with JavaScript and CSS

Once your REST API endpoint is active, you can query it directly using modern JavaScript (Fetch API) from your frontend application or theme scripts.

Frontend JavaScript Code

Here is an example script that fetches data from our endpoint and renders project cards onto the webpage dynamically:

document.addEventListener('DOMContentLoaded', function () {
    const container = document.getElementById('portfolio-grid');

    if (!container) return;

    // Fetch dynamic project data from custom REST API
    fetch('/wp-json/sp-portfolio/v1/projects?limit=3')
        .then(response => {
            if (!response.ok) {
                throw new Error('Network response was not ok');
            }
            return response.json();
        })
        .then(data => {
            container.innerHTML = ''; // Clear loading placeholder

            data.forEach(project => {
                const card = document.createElement('article');
                card.className = 'portfolio-card';

                card.innerHTML = `
                    <img src="${project.thumbnail}" alt="${project.title}" class="portfolio-thumb" />
                    <h3 class="portfolio-title">${project.title}</h3>
                    <p class="portfolio-excerpt">${project.excerpt}</p>
                    <a href="${project.permalink}" class="portfolio-link">View Project</a>
                `;

                container.appendChild(card);
            });
        })
        .catch(error => {
            console.error('Fetch error:', error);
            container.innerHTML = '<p>Unable to load projects at this time.</p>';
        });
});

Testing Your Custom Endpoint

After implementing the PHP, JavaScript, and CSS code, it is important to test your API route thoroughly. Here are a few recommended ways to test:

  1. Browser Direct Access: Open https://yourdomain.com/wp-json/sp-portfolio/v1/projects in your browser to inspect raw JSON responses.
  2. Postman or Insomnia: Use API testing tools to test different request types (GET, POST, PUT), examine response headers, and verify payload performance.
  3. WP CLI: Run terminal commands like wp rest route list to verify registered routes instantly.
