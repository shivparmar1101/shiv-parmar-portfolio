In this post, I will walk you through the entire process of registering, building, securing, and consuming custom REST API endpoints in WordPress.

Why Create Custom REST API Endpoints?

Before jumping into code, let's understand why default endpoints might not always be enough:

  • Data Optimization: Default endpoints often return too much unnecessary metadata, inflating payloads. Custom endpoints let you serve light, targeted JSON structures.
  • Custom Business Logic: Complex tasks like calculating post statistics, processing multi-step forms, or aggregating data across multiple tables require custom handling.
  • Enhanced Security: You can apply fine-grained permission checks and strict input sanitization specific to your custom requirements.

Key Insight: Never expose raw database queries directly through your REST API endpoints. Always pass parameters through validate_callback and sanitize_callback layers before processing data on the server side.

Step 1: Understanding the rest_api_init Hook

In WordPress, custom REST API endpoints are registered using the register_rest_route() function, which must always be attached to the rest_api_init action hook.

The standard syntax for registering a route looks like this:

register_rest_route( string $namespace, string $route, array $args = array(), bool $override = false );

Let's break down the core components:

  1. Namespace: A unique prefix (e.g., shiv-api/v1) that prevents route collisions with other plugins or themes.
  2. Route: The endpoint path appended to the namespace (e.g., /latest-posts).
  3. Args: An array defining supported HTTP methods, callback functions, permission checks, and expected arguments.

Step 2: Registering Your First Custom Endpoint in PHP

Let's create a real-world scenario. Suppose we want to fetch a simplified list of recent posts containing only the post ID, title, excerpt, and permalink. Here is how we register this endpoint in our theme's functions.php file or a custom plugin:

<?php
/**
 * Register custom REST API route
 * Author: Shiv Parmar
 */

add_action('rest_api_init', 'shiv_register_custom_rest_routes');

function shiv_register_custom_rest_routes() {
    register_rest_route('shiv-api/v1', '/featured-posts', array(
        'methods'             => WP_REST_Server::READABLE, // HTTP GET
        'callback'            => 'shiv_get_featured_posts',
        'permission_callback' => 'shiv_get_featured_posts_permissions',
        'args'                => array(
            'limit' => array(
                'default'           => 5,
                'sanitize_callback' => 'absint',
                'validate_callback' => 'is_numeric',
            ),
        ),
    ));
}

Notice that we used WP_REST_Server::READABLE instead of writing 'GET'. Using built-in WordPress constants is recommended practice because it ensures compatibility across different environments.

Step 3: Writing Callback and Permission Functions

Now, let's implement the callback function that queries the database and formats our JSON response, along with the permission function.

<?php

/**
 * Permission Check
 */
function shiv_get_featured_posts_permissions() {
    // Return true to allow public access.
    // Replace with current_user_can('edit_posts') if restricted access is required.
    return true; 
}

/**
 * REST Endpoint Callback Function
 */
function shiv_get_featured_posts($request) {
    // Retrieve sanitized argument
    $limit = $request->get_param('limit');

    $args = array(
        'post_type'      => 'post',
        'posts_per_page' => $limit,
        'post_status'    => 'publish',
    );

    $query = new WP_Query($args);

    if (empty($query->posts)) {
        return new WP_Error('no_posts_found', 'No posts available', array('status' => 404));
    }

    $formatted_data = array();

    foreach ($query->posts as $post) {
        $formatted_data[] = array(
            'id'        => $post->ID,
            'title'     => get_the_title($post->ID),
            'excerpt'   => get_the_excerpt($post->ID),
            'permalink' => get_permalink($post->ID),
        );
    }

    // Wrap the response in WP_REST_Response for better HTTP standard handling
    return new WP_REST_Response($formatted_data, 200);
}

By returning a WP_REST_Response object, WordPress automatically formats our array into a clean JSON output with the HTTP status code 200 (Success).

Step 4: Consuming the Custom Endpoint with JavaScript

Now that our endpoint is active at https://yourdomain.com/wp-json/shiv-api/v1/featured-posts?limit=3, let's fetch this data on the front end using native JavaScript (Fetch API).

document.addEventListener('DOMContentLoaded', () => {
    const container = document.getElementById('featured-posts-container');

    if (!container) return;

    fetch('/wp-json/shiv-api/v1/featured-posts?limit=3')
        .then(response => {
            if (!response.ok) {
                throw new Error('Network response was not ok');
            }
            return response.json();
        })
        .then(data => {
            let htmlContent = '';
            data.forEach(post => {
                htmlContent += `
                    <article class="api-card">
                        <h3 class="api-card-title"><a href="${post.permalink}">${post.title}</a></h3>
                        <p class="api-card-excerpt">${post.excerpt}</p>
                    </article>
                `;
            });
            container.innerHTML = htmlContent;
        })
        .catch(error => {
            console.error('Error fetching REST data:', error);
            container.innerHTML = '<p>Failed to load posts. Please try again later.</p>';
        });
});

Best Practices for Production-Ready REST APIs

Building functional REST routes is only half the battle. To ensure your custom API scales reliably in production environments, keep these best practices in mind:

  • Always Require Permission Callbacks: Since WordPress 5.5, omitting permission_callback will trigger a PHP notice. If public access is intentional, explicitly return __return_true.
  • Leverage Transients for Heavy Queries: If your API endpoint runs expensive DB queries, cache the computed JSON result using WordPress Transients API to reduce server load.
  • Use Nonces for Non-GET Requests: When submitting data via POST, PUT, or DELETE, ensure you validate WordPress REST nonces (X-WP-Nonce header) to safeguard against CSRF attacks.
