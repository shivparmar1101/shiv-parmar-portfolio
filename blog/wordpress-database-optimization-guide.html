1. Controlling Revisions and Trash Retention

By default, WordPress stores every single revision of every post and page you save. On a blog with hundreds of posts, you might end up with thousands of unnecessary database rows in your wp_posts table.

To fix this, we can easily limit post revisions and shorten trash retention time right inside your wp-config.php file. Add these lines near the top of the file:

// Limit post revisions to 5 per post
define( 'WP_POST_REVISIONS', 5 );

// Empty trash automatically every 7 days instead of 30
define( 'EMPTY_TRASH_DAYS', 7 );

If you want to clear out existing historical revisions in one clean query, you can run this SQL command via phpMyAdmin or MySQL CLI:

DELETE a, b, c
FROM wp_posts a
LEFT JOIN wp_term_relationships b ON (a.ID = b.object_id)
LEFT JOIN wp_postmeta c ON (a.ID = c.post_id)
WHERE a.post_type = 'revision';

Note: Always create a complete database backup before executing manual SQL delete operations!

2. Taming the Autoloaded Data Bloat

One of the most common performance bottlenecks I diagnose during database audits is a bloated wp_options table. When WordPress loads a page, it fetches all rows where autoload = 'yes' in a single query.

Ideally, total autoloaded data should be under 800 KB. If it exceeds 2 MB, your server overhead spikes instantly.

Finding Autoload Size via SQL

Run this query to check the exact total size of autoloaded options in megabytes:

SELECT SUM(LENGTH(option_value)) / 1024 / 1024 AS autoload_size_mb 
FROM wp_options 
WHERE autoload = 'yes';

Identifying Heavy Autoload Options

To see which plugins or themes are cluttering your memory, list the top 10 largest autoloaded options:

SELECT option_name, LENGTH(option_value) AS option_size
FROM wp_options
WHERE autoload = 'yes'
ORDER BY option_size DESC
LIMIT 10;

Once identified, you can either set autoload = 'no' for non-critical options or remove leftovers from uninstalled plugins using custom PHP or SQL.

3. Cleaning Up Expired Transients Programmatically

Transients are WordPress’s temporary caching mechanism stored in the wp_options table. Sometimes, expired transients are not automatically removed, leaving thousands of dead rows behind.

Here is a lightweight PHP snippet you can place in your child theme's functions.php or inside a custom maintenance plugin to purge expired transients automatically using custom scheduled tasks:

<?php
/**
 * Programmatically purge expired transients in WordPress.
 */
function shiv_purge_expired_transients() {
    global $wpdb;

    $time = time();
    $sql = "
        DELETE a, b
        FROM {$wpdb->options} a
        JOIN {$wpdb->options} b ON b.option_name = REPLACE(a.option_name, '_timeout', '')
        WHERE a.option_name LIKE '\_transient\_timeout\_%'
        AND a.option_value < %d
    ";

    $wpdb->query( $wpdb->prepare( $sql, $time ) );
}

// Hook into custom cron schedule
add_action( 'shiv_daily_db_cleanup', 'shiv_purge_expired_transients' );

if ( ! wp_next_scheduled( 'shiv_daily_db_cleanup' ) ) {
    wp_schedule_event( time(), 'daily', 'shiv_daily_db_cleanup' );
}

4. Optimizing Post Meta Queries and Indexes

As a developer building complex WooCommerce platforms or custom directory sites, slow database queries are usually caused by bad meta_query usage. Searching by unindexed meta values inside wp_postmeta forces full table scans.

"A database without proper indexing and maintenance strategy is like a library without a catalog system. The larger it grows, the longer it takes to find a single piece of information."

When creating custom features that require heavy querying, consider creating dedicated custom MySQL tables with appropriate indexes using the native dbDelta function instead of dumping everything into wp_postmeta.

<?php
/**
 * Create custom table with proper database indexes.
 */
function shiv_create_custom_log_table() {
    global $wpdb;

    $table_name = $wpdb->prefix . 'custom_user_logs';
    $charset_collate = $wpdb->get_charset_collate();

    $sql = "CREATE TABLE $table_name (
        id bigint(20) NOT NULL AUTO_INCREMENT,
        user_id bigint(20) NOT NULL,
        action_type varchar(50) NOT NULL,
        created_at datetime DEFAULT CURRENT_TIMESTAMP NOT NULL,
        PRIMARY KEY  (id),
        KEY user_id_index (user_id),
        KEY action_type_index (action_type)
    ) $charset_collate;";

    require_once( ABSPATH . 'wp-admin/includes/upgrade.php' );
    dbDelta( $sql );
}
register_activation_hook( __FILE__, 'shiv_create_custom_log_table' );

5. Optimizing MySQL Tables via WP-CLI

For developers who love command-line workflows like me, WP-CLI is the fastest tool to perform structural maintenance on MySQL tables. Over time, deleting records leaves physical overhead space on disk, causing table fragmentation.

Here are the step-by-step commands I run during routine server maintenance:

  1. Check Database Status: Verify table integrity across the schema. 
    wp db check
  2. Optimize All Tables: Defragment tables to reclaim disk space and rebuild indexes. 
    wp db optimize
  3. Clean All Expired Transients: Instantly remove stored transient data via terminal. 
    wp transient delete --expired

Summary Checklist for Database Optimization

To keep your site running smoothly, here is a quick summary checklist you can follow every month:

  • Limit post revisions in wp-config.php.
  • Delete orphaned postmeta, termmeta, and commentmeta rows.
  • Monitor and keep autoload size under 1 MB in wp_options.
  • Purge expired transients regularly via scheduled PHP cron tasks or WP-CLI.
  • Optimize MyISAM/InnoDB tables to reduce fragment overhead.

Database optimization isn't a one-time setup; it is an ongoing maintenance discipline. By writing clean code, controlling data bloat, and running regular upkeep scripts, you ensure that your WordPress installations remain fast, stable, and scalable regardless of traffic demands.
