    1. Controlling Post Revisions and Trash Retention

    By default, WordPress stores an infinite number of post revisions. If you edit an article 30 times, WordPress saves 30 full copies of that article in your wp_posts table. Multiply that across hundreds of posts, and you have thousands of unnecessary rows cluttering your database and slowing down queries.

    To control this, open your wp-config.php file and limit the number of revisions WordPress retains. You can also shorten the time items remain in the trash before being permanently deleted.

    // Limit post revisions to 5 per post
define( 'WP_POST_REVISIONS', 5 );

// Empty trash automatically every 7 days (default is 30)
define( 'EMPTY_TRASH_DAYS', 7 );

    If you want to completely disable revisions on dynamic news or e-commerce sites, you can set WP_POST_REVISIONS to false. However, retaining 3 to 5 revisions is generally a safer middle ground for content editors.

    2. Taming the Autoloaded Data in `wp_options`

    The wp_options table is often the single biggest contributor to high Time to First Byte (TTFB). Every time a user visits any page on your website, WordPress loads all database rows where the autoload column is set to yes in a single query.

    If your autoloaded data exceeds 800 KB to 1 MB, server performance starts degrading. I often see sites built with visual builders or unoptimized plugins carrying 5 MB to 10 MB of autoloaded data!

    Identifying Heavy Autoloaded Options

    You can run this SQL query in phpMyAdmin or MySQL CLI to list the largest autoloaded options on your site:

    SELECT option_name, LENGTH(option_value) AS option_size 
FROM wp_options 
WHERE autoload = 'yes' 
ORDER BY option_size DESC 
LIMIT 20;

    If you spot options from deleted plugins or massive transient caches, you should safely remove them or update their autoload status to no.

    Cleaning Expired Transients Programmatically

    Transients are temporary cached options, but expired transients often remain in the wp_options table longer than necessary. You can drop this custom PHP function into your theme's functions.php or a custom maintenance plugin to clean them automatically:

    function shiv_clean_expired_transients() {
    global $wpdb;
    
    $time = time();
    $sql = "DELETE a, b FROM {$wpdb->options} a
            INNER JOIN {$wpdb->options} b 
            ON b.option_name = REPLACE(a.option_name, '_timeout_', '')
            WHERE a.option_name LIKE '\_transient\_timeout\_%'
            AND a.option_value < %d";
            
    $deleted = $wpdb->query( $wpdb->prepare( $sql, $time ) );
    return $deleted;
}
    A bloated database is often the hidden bottleneck behind poor TTFB (Time to First Byte). You can add all the page caching plugins you want, but if your database queries take seconds to execute due to unindexed metadata or gigabytes of autoloaded options, your site will never feel truly responsive.

    3. Removing Orphaned Post Metadata and Term Relationships

    When you delete a post, page, or product, WordPress sometimes leaves behind "orphaned" metadata in wp_postmeta, or unused tag/category relationships in wp_term_relationships. Over time, these orphaned rows take up valuable space and slow down join queries.

    Here is how you can clean up orphaned post meta safely using a direct SQL query:

    DELETE pm 
FROM wp_postmeta pm 
LEFT JOIN wp_posts wp ON wp.ID = pm.post_id 
WHERE wp.ID IS NULL;

    Similarly, you can remove orphaned term relationships where the post no longer exists:

    DELETE tr 
FROM wp_term_relationships tr 
LEFT JOIN wp_posts wp ON wp.ID = tr.object_id 
WHERE wp.ID IS NULL;

    Note: Always create a full database backup before executing direct DELETE queries on production environments!

    4. Automating Database Maintenance with WP-Cron

    Instead of running manual queries every month, I prefer automating routine maintenance tasks. We can attach a cleanup function to a custom scheduled task using WordPress's internal cron system.

    Here is an example script that schedules a weekly database cleanup for transients and spam comments:

    // Schedule weekly event if not already scheduled
if ( ! wp_next_scheduled( 'shiv_weekly_db_cleanup_event' ) ) {
    wp_schedule_event( time(), 'weekly', 'shiv_weekly_db_cleanup_event' );
}

add_action( 'shiv_weekly_db_cleanup_event', 'shiv_run_database_cleanup' );

function shiv_run_database_cleanup() {
    global $wpdb;

    // 1. Delete spam comments
    $wpdb->query( "DELETE FROM {$wpdb->comments} WHERE comment_approved = 'spam'" );

    // 2. Delete trashed comments
    $wpdb->query( "DELETE FROM {$wpdb->comments} WHERE comment_approved = 'trash'" );

    // 3. Delete expired transients
    shiv_clean_expired_transients();

    // 4. Optimize core tables
    $wpdb->query( "OPTIMIZE TABLE {$wpdb->posts}, {$wpdb->postmeta}, {$wpdb->options}" );
}

    5. Converting Legacy Storage Engines to InnoDB

    If your WordPress site has been around for several years, some of your database tables might still be using the older MyISAM storage engine. Modern WordPress development strongly favors InnoDB.

    Why InnoDB is Superior for WordPress:

    • Row-level Locking: MyISAM locks the entire database table during an update, causing queue delays. InnoDB only locks the specific row being modified.
    • ACID Compliance: InnoDB offers better reliability and prevents database corruption during server crashes.
    • Better Memory Utilization: InnoDB utilizes the innodb_buffer_pool_size setting in MySQL to cache both data and indexes efficiently in RAM.

    You can check your table engines in phpMyAdmin. If you find tables using MyISAM, convert them to InnoDB using the following SQL statement:

    ALTER TABLE wp_posts ENGINE = InnoDB;
ALTER TABLE wp_postmeta ENGINE = InnoDB;
ALTER TABLE wp_options ENGINE = InnoDB;

    Best Practices Summary for WordPress Developers

    To ensure your clients' sites stay fast over the long term, build these habits into your regular workflow:

    1. Audit Plugins Regularly: Deactivate and delete plugins that leave orphaned options or heavy custom tables behind.
    2. Keep Autoloaded Options Under 800 KB: Periodically check `wp_options` size.
    3. Maintain Staging Backups: Always run database optimizations on a staging environment first to verify stability.
    4. Use Offsite Backups: Before running custom SQL cleanups, take a full database snapshot using tools like WP-CLI, UpdraftPlus, or server-level backups.

    Final Thoughts

    Database optimization is not a one-time project—it is an ongoing maintenance duty for serious WordPress developers. By keeping your revisions under control, auditing autoloaded data in wp_options, converting to InnoDB, and automating cleanup tasks, you can ensure your WordPress sites remain blazing fast regardless of traffic or content size.
